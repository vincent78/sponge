# 06. 配置、测试、部署与实战路线

## 配置如何进入程序

默认配置位于 `configs/serverNameExample.yml`。启动入口接受 `-c` 指定文件；未指定时通过 `configs.Location` 定位默认配置。`internal/config` 的生成结构调用 `pkg/conf.Parse` 反序列化，并通过 `Get()` 暴露只读式全局入口。

主要开关：

- `app`：环境、名称、版本、cache 类型、metrics/trace/stat/限流/熔断、注册发现类型；
- `http`、`grpc`：端口、超时、TLS/token；
- `database`、`redis`：连接与连接池；
- `logger`、`jaeger`：日志和链路追踪；
- etcd/consul/nacos 及 gRPC clients。

配置初始化必须早于 router/server，因为构造中已经读取 `config.Get()`。测试若绕过 main，需要先 `config.Set` 或执行测试初始化。

## 测试分层

仓库大量采用同包单元测试，命名为 `*_test.go`：

- parser/replacer/gofile 等生成工具：用固定输入比较生成文本和文件结果；
- DAO：常用 sqlmock 或测试数据库验证 SQL、事务和错误映射；
- cache：memory/miniredis 验证 key、TTL、序列化；
- handler：构造 Gin test context/httptest，验证状态码和统一响应；
- service：直接调用 RPC 方法，另有 client test 做接近集成测试的调用；
- middleware/interceptor：验证上下文传播、异常、鉴权与指标。

基本命令：

```bash
go test ./...
go test ./pkg/sql2code/parser -run TestName -v
go test ./internal/handler -run TestName -v
go test -race ./pkg/app ./pkg/cache
```

完整 `./...` 可能需要数据库、Redis、注册中心、生成插件或系统能力。失败时先区分纯单测失败还是外部依赖缺失，不要为了“变绿”删除集成测试断言。

## 构建与生成

根 Makefile 同时服务模板仓库开发，生成项目里的 Makefile 会按项目形态裁剪。常见目标包括：

- `make proto`：protoc 生成 pb、validate、gateway/OpenAPI 等；
- `make docs`：swag 生成 HTTP Swagger；
- `make run`：编译/运行服务；
- lint/test/build/image/deploy 相关目标。

`scripts/protoc.sh` 明确记录插件顺序和 include path。遇到 pb 生成差异时，检查插件版本、third_party 路径和脚本，而不是手改 pb.go。

## 部署资产

- `scripts/build`：多阶段/本地 Docker 构建模板；
- `deployments/docker-compose`：服务和依赖的组合启动；
- `deployments/kubernetes`：Deployment、Service、ConfigMap 等模板；
- image repo、project/server name 在生成阶段替换。

server 的优雅退出与 readiness/health、注册中心注销相互关联。生产发布时需要给进程足够 termination grace period，使 `app.stop()` 完成。

## 推荐的本地阅读实验

### 实验一：只追踪启动

在 `main`、`InitApp`、`CreateServices`、`app.Run`、`httpServer.Start` 打断点。先不请求 API，观察配置、DB、server 的初始化顺序，再发送 SIGINT 看 close 顺序。

### 实验二：追踪一个 HTTP GetByID

依次在 router、handler、DAO、cache/database 打断点，分别观察缓存未命中、命中、记录不存在三条路径。记录每层输入输出类型。

### 实验三：只运行 parser

用一条最小 `CREATE TABLE` 调 `sql2code.Generate`，打印 map 中每个 code type。再改变主键、nullable、JSON 命名和 extended API，比较输出。这是理解生成器最快的方法。

### 实验四：观察模板选择

阅读 `httpGenerator.generateCode` 的 `subDirs/subFiles/selectFiles`，分别代入 mysql、mongodb、普通 ID、复合/非标准主键、mono-repo，列出会选中的文件变体。

## 修改需求到源码位置

| 需求 | 优先查找 |
|---|---|
| 新增 CLI 子命令 | `cmd/sponge/commands/root.go` 和新 command 文件 |
| 改生成字段类型 | `pkg/sql2code/parser` 的类型映射与模板 |
| 改生成项目结构 | `cmd/sponge/commands/generate/*Generator.generateCode` |
| 改占位替换规则 | `pkg/replacer` 和 generator fields |
| 增加 HTTP 横切能力 | `pkg/gin/middleware`，再在 `internal/routers` 接入 |
| 增加 gRPC 横切能力 | `pkg/grpc/interceptor`，再在 `internal/server/grpc.go` 接入 |
| 改 CRUD 语义 | handler/service + DAO 模板；必要时同时改 cache 和测试 |
| 新增注册中心 | `pkg/servicerd/registry` 实现及 server initial option |
| 修改 API | proto 或 HTTP types/handler 注释，然后重新生成文档 |

## 提交前检查清单

1. 修改的是源模板还是生成结果？两者是否需要同步？
2. HTTP、gRPC、pb、MongoDB、extended API、mono-repo 变体是否受影响？
3. 模板 mark 和占位符是否仍唯一存在？
4. 生成后的代码能否 gofmt、编译，import 是否正确？
5. 新 option 是否有合理默认值，旧配置是否兼容？
6. Start 成功后的资源是否在 Stop 中释放？
7. 错误是否保留 request ID/trace，且不会把 DSN/token 泄露给响应或日志？
8. 是否补了最小单测与一次真实生成 smoke test？

## 最后的阅读原则

不要试图线性读完每一个文件。先掌握两条主链，再按问题深入包：生成问题沿 CLI→parser→generator→replacer，运行问题沿 main→server→transport→business→data。能画出数据和控制权在每层如何变化，就已经真正读懂了这套源码的骨架。
