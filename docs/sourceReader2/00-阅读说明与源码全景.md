# 00. 阅读说明与源码全景

## 1. 仓库到底包含什么

当前仓库约有 609 个 Go 文件、197 个 Go 测试文件和 49 个模板变体。它把以下内容放在同一个 module 中：

1. Sponge CLI 和本地可视化生成服务；
2. protoc 插件与代码生成算法；
3. 一套可被复制的 HTTP/gRPC 项目模板；
4. 生成项目使用的通用 `pkg` 基础库；
5. 测试、构建、容器和 Kubernetes 交付素材。

因此，“阅读整个工程”不是从根目录任意找一个 main 开始，而是先分清哪些代码在生成时运行，哪些代码在生成后的服务里运行。

## 2. 顶层目录逐项说明

| 路径 | 角色 | 是否属于 Sponge CLI | 是否进入生成项目 |
|---|---|---:|---:|
| `cmd/sponge` | CLI、UI 后端、生成/合并/修补/压测命令 | 是 | 否 |
| `cmd/protoc-gen-*` | 自定义 protoc 插件 | 是 | 通常只产出代码 |
| `cmd/serverNameExample_*` | 多种服务形态的启动模板 | 否 | 是，按模式选择 |
| `api` | 示例 proto 及生成的 pb 文件 | 否 | 是 |
| `internal` | 生成项目的私有业务与基础设施层 | 否 | 是，按模式选择 |
| `pkg` | 可复用运行时和生成器基础库 | 部分被 CLI 使用 | 是，按依赖使用 |
| `configs` | 默认配置定位和 YAML | 否 | 是 |
| `docs` | Swagger 等文档生成物 | 否 | 是 |
| `scripts` | protoc、构建、镜像脚本 | 支撑开发 | 是 |
| `deployments` | binary/Compose/Kubernetes | 否 | 是 |
| `third_party` | Proto 编译依赖 | 支撑插件 | 是 |
| `test` | 集成环境、SQL 样本、自动测试 | 验证 | 否或按需复制 |

## 3. 怎样识别模板变体

同一逻辑存在多种文件后缀：

- `.tpl`：非标准主键等“通用 CRUD”模板；
- `.exp`：扩展 API 模板，通常从基础 5 个 API 扩展到 9 个；
- `.mgo`：MongoDB 实现；
- `.noregistry`：不接入注册中心的 server 版本；
- 普通 `.go`：标准关系型数据库、标准整数 ID 的默认模板。

这些文件不是由 Go 编译器同时编译。生成器通过白名单选中某一变体，再去除特殊后缀或写入目标位置。

源码中的以下注释是生成协议的一部分：

```text
// todo generate ... here
// delete the templates code start
// delete the templates code end
```

它们分别充当插入锚点和删除区间。修改注释文字可能破坏生成器。

## 4. 生成文件与手写文件

遇到 `Code generated ... DO NOT EDIT` 时，应回溯它的来源：

- `*.pb.go`、`*_grpc.pb.go`、validate/gateway 文件来自 `.proto`；
- Swagger Go/JSON/YAML 来自注释或 proto OpenAPI 注解；
- `internal/config` 的结构体来自 YAML 配置生成；
- 某些项目文件来自 Sponge 模板替换。

重新实现时要明确“事实来源”。对生成结果直接修补只适合临时验证，正式修改应落在 schema、模板或生成算法。

## 5. 推荐源码阅读动作

### 第一步：找入口

```bash
rg 'func main\(' cmd
```

主入口包括 Sponge CLI、各服务形态和 protoc 插件。

### 第二步：找构造函数和接口

```bash
rg 'func New[A-Z]' cmd internal pkg
rg 'var _ .*=' internal pkg
```

`NewXxx` 展示依赖组装；`var _ Interface = (*impl)(nil)` 展示实现关系。

### 第三步：找隐式注册

```bash
rg 'func init\(|registerFns|RouterFns' internal cmd
```

HTTP 路由、gRPC service、模板和命令常通过包级初始化注册。

### 第四步：读测试

测试通常比实现更直接地表达默认值、边界和预期错误。先读公开 API 的测试，再进入内部辅助函数。

## 6. 阅读时建立的四张表

建议自己维护四张小表：

1. **入口表**：命令或请求从哪个函数进入；
2. **数据变换表**：输入类型怎样逐步变成输出类型；
3. **资源表**：连接、goroutine、文件和 server 由谁创建、谁关闭；
4. **变体表**：数据库/协议/API 模式改变时选择哪个实现。

这四张表足以避免在大型模板仓库中迷路。

## 7. 重实现时的边界

第一版不应同时实现所有 50 多个 `pkg`。真正的最小闭环是：读取一份 MySQL DDL → 生成 model/DAO/HTTP DTO → 复制一个可运行 Gin 项目 → 通过单测。之后再增加在线数据库、gRPC、MongoDB、注册发现和可观测性。
