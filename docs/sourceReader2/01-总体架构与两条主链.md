# 01. 总体架构与两条主链

## 1. 系统上下文

Sponge 面向两类使用者：开发者通过 CLI/UI 描述项目，生成出的服务则面对 API 调用者和基础设施。

```text
开发者
  ├─ CLI 参数 ───────────────┐
  ├─ Web UI ─→ 本地 UI API ──┤
  ├─ SQL/数据库 ─────────────┤
  ├─ Proto ──────────────────┤
  └─ 自定义模板 ─────────────┘
                ↓
          Sponge 生成引擎
                ↓
       普通 Go 服务工程 + 文档 + 测试 + 部署文件
                ↓
 API 调用者 / DB / Redis / 注册中心 / 消息系统 / 可观测平台
```

## 2. 生成期主链

以 `sponge web http` 为代表：

```text
cmd/sponge/main.go
  → generate.Init：检查 ~/.sponge，创建 replacer
  → commands.NewRootCMD：构造 Cobra 命令树
  → HTTPCommand.RunE：收集参数、拆分多表
  → sql2code.Generate：schema → 多类字段代码
  → httpGenerator.generateCode：决定项目形态和模板集合
  → addFields：组装替换规则
  → replacer.SaveFiles：复制、替换、输出
  → saveGenInfo / configmap 等后处理
```

生成期有三个层次：

| 层 | 关心内容 | 不应关心内容 |
|---|---|---|
| schema/parser | 表、列、主键、类型、命名 | 输出目录、Docker、server 端口 |
| generator | 生成哪种项目、选哪些文件、插哪些片段 | SQL AST 的细节 |
| replacer | 文件选择、文本替换、输出 | CRUD 业务语义 |

良好的重实现也应保持这三层分离，否则新增数据库或模板形态会导致大量条件分支交叉。

## 3. UI 不是第二套生成器

`sponge run` 启动 `cmd/sponge/server`，它嵌入前端静态文件并提供 `/api/v1/generate`。后端接收前端拼出的参数后，再启动本机 `sponge` 子进程，把生成目录压缩为 zip 返回。

因此 UI 是 CLI 的适配层：

```text
表单 → 命令参数字符串 → sponge 子进程 → 临时目录 → zip 下载
```

这个设计保证 CLI 与 UI 行为一致，代价是必须正确处理参数解析、命令超时、临时文件清理和子进程错误。

## 4. HTTP 运行期主链

```text
cmd/..._httpExample/main.go
  → initial.InitApp
      → config → logger → tracer/stat → database/cache
  → initial.CreateServices
      → server.NewHTTPServer → routers.NewRouter
  → app.Run
      → server.Start + signal watcher

HTTP request
  → net/http → Gin Engine
  → recovery/CORS/timeout/requestID/log/metrics/... middleware
  → router group
  → handler：绑定与校验、DTO/model 转换、错误响应
  → DAO：查询语义、事务和缓存协调
  → GORM/MongoDB + memory/Redis
  → 统一 response
```

这里的核心边界是：router 只做 URL 到 handler 的映射；handler 只适配 HTTP；DAO 承担持久化查询语义；database/cache 包管理具体连接。

## 5. gRPC 运行期主链

```text
main / initial / app
  → server.NewGRPCServer
  → TLS + unary/stream interceptor chain
  → 遍历 service registerFns 注册 generated service
  → listener.Serve

RPC request
  → generated stub 解码
  → recovery/requestID/log/auth/metrics/limit/breaker/trace interceptor
  → service：Validate、protobuf/model 转换、业务编排
  → 共用 DAO/cache/database
  → ecode 转 gRPC status
```

Gateway/混合模式改变 transport 组合，但不会改变数据层主链。

## 6. 生命周期主链

`pkg/app` 把不同 server 抽象为：

```go
type IServer interface {
    Start() error
    Stop() error
    String() string
}
```

`errgroup` 并发运行所有 server 和信号 watcher。任一 Start 返回错误会取消 context；SIGINT/SIGTERM/SIGHUP 会顺序执行 close 函数。SIGTRAP 用于切换 profile。

资源所有权必须成对：

```text
registry Register ↔ Deregister
HTTP ListenAndServe ↔ Shutdown
gRPC Serve ↔ GracefulStop
DB/Redis Init ↔ Close
tracer Init ↔ Close
logger Init ↔ Sync
```

## 7. 数据模型为什么分三层

- `internal/model`：数据库形态，含 GORM/BSON tag；
- `internal/types`：HTTP 请求/响应形态，含 JSON/binding tag；
- `api/...pb.go`：gRPC/Proto 契约形态，含 wire number 和 validate。

三者通过 copier 和少量显式转换连接。它们不能合并成一个 struct，因为数据库可空性、API 安全字段和协议兼容性有不同演进规则。

## 8. 错误模型

`pkg/errcode` 提供通用 HTTP/RPC 错误对象和转换；`internal/ecode` 存放生成项目的系统/业务错误。内部日志记录底层 error 与 request ID，对外只返回稳定 code/message，避免泄露 SQL、DSN、栈或内部拓扑。

## 9. 配置驱动的可选能力

配置决定 cache、TLS、metrics、trace、profile、rate limit、circuit breaker、registry/discovery 等。大部分能力通过 functional option 或 middleware/interceptor 接入，不侵入 handler/service。

重实现时先用显式构造参数，功能稳定后再引入 options；不要一开始复制所有配置开关。
