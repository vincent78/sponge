# 04 代码生成器与模板写入机制

## 1. 两阶段生成，而不是一个大模板

Sponge 的工程生成可以拆成：

```text
数据库/Proto
  → 结构化信息及代码片段
  → 从 ~/.sponge 选择骨架文件
  → replacer 做内容、名称和路径替换
  → 写到输出目录
```

第一阶段的 SQL 细节在 `pkg/sql2code`；本篇关注 `cmd/sponge/commands/generate` 如何消费结果。代码片段 map 的 key 来自 `parser`，例如 model、table name、handler request/reply、DAO update fields。Generator 把它们塞进模板预留标记。

## 2. 模板注册

`generate.Init` 为磁盘目录 `~/.sponge` 建立名为 `sponge` 的 Replacer，保存到全局 `Replacers`。`InitFS` 允许其他包注册 embed.FS 模板，重名会 panic。这里的全局表方便命令使用，但重实现时更适合依赖注入 `TemplateRegistry`，测试无需修改全局状态。

关键约定：

- `.tpl`：模板变体；
- `.mgo`：MongoDB 变体；
- `.exp`：扩展 API 变体；
- `// todo generate ... here`：插入点；
- `// delete the templates code start/end`：最终生成时删除的示例区域；
- `UserExample`、`serverNameExample`：内容和文件路径里的占位名字。

## 3. 每个 generator 的标准流程

以 `modelGenerator.generateCode` 为最小样本：

```go
r := Replacers["sponge"]
r.SetSubDirsAndFiles(nil, "internal/model/userExample.go")
r.SetReplacementFields(fields)
r.SetOutputDir(outPath, "model")
r.SaveFiles()
```

`addFields` 先删除模板示例块，再把 `modelFileMark` 替换为 SQL 解析产生的 struct，并将 `UserExample` 大小写敏感替换成真实对象名。真正的大型 generator 仍是这四步，只是文件选择和 fields 更多。

## 4. 完整 HTTP 工程

`httpGenerator.generateCode` 每次新建磁盘 Replacer，选择：

- `cmd/serverNameExample_httpExample` 启动入口；
- `sponge/configs/deployments/scripts` 运维文件；
- go.mod、Makefile、README 等根文件；
- cache/config/dao/database/ecode/handler/model/routers/server/types 等内部文件。

然后 `SetSelectFiles` 根据数据库类型选择普通文件还是 `.mgo` 版本；扩展 API 再选择 `.exp` 内容。字段替换负责：模块名、服务名、项目名、镜像地址、DSN/driver、数据库初始化、model/DAO/types/handler 代码、路由注册、Docker/Kubernetes 片段、Go 版本等。

保存后，多表中的后续表不再复制整棵工程，而由 `handlerGenerator` 定点增加 model/cache/dao/ecode/handler/types/router 文件。由此可知第一张表不是业务上更重要，而是承担“创建骨架”的职责。

## 5. RPC 与 Proto 工程

`rpcGenerator` 选择 grpc main、third_party、proto、model/dao/cache、service/server 等。SQL 先产生第一份 `.proto` 和 service 模板；用户执行 `make proto` 后，protoc 插件再把 proto 变成 Go 路由和可合并逻辑文件。因此 RPC 生成有两个时间点：

```text
sponge micro rpc       创建项目与 proto
make proto              protoc 标准插件 + Sponge 插件
sponge merge rpc-pb     合并增量逻辑
```

`rpc-pb`、`rpc-gw-pb`、`http-pb` 则以用户已有 proto 为源，先复制 proto/third_party，再调整 protoc 脚本。`grpc-http`/`grpc-http-pb` 组合两套 server 初始化。重实现时要把“项目模板类型”建模为显式枚举，避免散落的布尔组合。

## 6. 文件选择和变体

选择逻辑的目的不是复制整个仓库，而是建立白名单：`subDirs` 可整目录复制，`subFiles` 精确复制，`selectFiles` 指定目录下文件。数据库适配通常遵循：

1. MongoDB 选 `.mgo`；关系库选普通文件。
2. 开启 extended API 时叠加 `.exp`。
3. 保存时去掉这些模板后缀，得到正常 `.go` 文件。
4. mono-repo 模式去掉服务自身 go.mod/go.sum，并调整模块 import 与输出层级。

白名单是安全边界：新增模板文件不会自动进入生成物。复刻时应为每种 project profile 写可测试 manifest，并检测目标路径冲突。

## 7. 内容清理与修正

`common.go` 有许多生成后规则：

- 删除开始/结束标记包围的示例代码；
- 替换整文件或某个 marker；
- MongoDB 的 ID 转 string；普通非 common style 的 ID 修为 uint64；
- kebab-case 项目名、连字符服务名转下划线；
- 根据实际用法删除无用 import 或模板段；
- 注入 HTTP/gRPC 不同的 Docker、Compose、K8s 探针和端口片段。

这说明模板系统不只是 `text/template`。它是“文件筛选 + 字符串替换 + 标记剪裁 + 路径重命名”。字符串规则对格式敏感，重实现更稳妥的做法是：模板用 `text/template` 生成完整文件；对已有 Go 文件的修改用 AST；运维 YAML 使用结构化 YAML 或独立模板。

## 8. 自定义 template 命令

`template field`：读模板文件与 JSON fields，执行自定义模板。`template sql`：从数据库取得表信息，合并用户 fields 后执行。`template protobuf`：复制依赖 proto，用 protoc 转 JSON，再解析为 map，与用户 fields 合并执行。

三者共享 `parseFields`、`mergeFields` 和结果信息输出。合并时同名字段的覆盖顺序必须在复刻中明确；模板错误、JSON 类型不符、protoc 不可用均应原样返回上下文。

## 9. 写入安全与幂等性

- 全项目生成不应覆盖已有同名输出；增量生成则必须能写到既有项目。
- 字符串占位符若也出现在用户注释/业务文本中，可能误替换。
- marker 被用户删掉后，增量生成可能静默少代码。
- 一次 SaveFiles 涉及多文件，非事务式；失败可能留下部分文件。
- 模板版本与 CLI/插件版本必须绑定。

推荐复刻流程：先把所有输出渲染进临时目录，运行 `gofmt` 和静态校验，生成 manifest，最后 rename 到目标；增量修改先备份并输出 diff。

## 10. 最小重实现练习

1. 写一个只包含 `model/user.go.tpl` 的模板。
2. 定义 `ModelData{Name, Fields}`，禁止传松散 map。
3. 渲染到临时目录，gofmt 后移动。
4. 加 MySQL 与 Mongo 两个 profile，测试 ID 类型差异。
5. 再加入 DAO/handler，并将每个输出文件快照测试。
6. 最后实现“第一表建骨架、后续表增量”的项目级编排。
