# 08 运行时启动、初始化与优雅退出

这一章回答一个最基本的问题：生成出来的工程执行以后，第一行到最后一行究竟做了什么。建议先读本章，再读 HTTP、gRPC 和数据层。

## 1. 七种可生成的服务骨架

`cmd/serverNameExample_*Example` 是“生成后工程”的可执行入口样板，不是生成器 CLI 本身：

| 目录 | 对外能力 | 业务实现入口 |
|---|---|---|
| `httpExample` | 手写 Gin HTTP | `handler.UserExampleHandler` |
| `httpPbExample` | Proto 定义、Gin 承载 HTTP | `handler.userExamplePbHandler` |
| `grpcExample` | 手写/生成 gRPC 服务 | `service.UserExampleServer` |
| `grpcPbExample` | Proto gRPC | `service.UserExampleServer` |
| `grpcHttpPbExample` | 同进程同时启动 gRPC 与 Gin HTTP | service + handler |
| `grpcGwPbExample` | gRPC 服务加 grpc-gateway | service，经 Gateway 转发 |
| `mixExample` | 组合服务样板 | 按生成结果组合 |

每个目录几乎都有 `main.go` 和 `initial/{initApp,createService,close}.go`。这种重复是有意的：生成器复制选定骨架后，目标工程只留下所需入口。

## 2. main 的四行主干

```go
initial.InitApp()
services := initial.CreateServices()
closes := initial.Close(services)
app.New(services, closes).Run()
```

可以把它重新实现成四个阶段：准备全局依赖、组装服务器、登记清理函数、交给生命周期管理器运行。`app.IServer` 只要求 `Start() error`、`Stop() error` 和 `String() string`，所以 HTTP 与 gRPC 可以被同一种容器管理。

## 3. InitApp 的准确顺序

1. `initConfig` 注册 `-version`、`-c` 参数并 `flag.Parse()`。
2. 未传 `-c` 时使用 `configs.Location("serverNameExample.yml")`，然后 `config.Init`。
3. 命令行 `-version` 非空时覆盖 YAML 中版本。
4. `logger.Init` 根据 level、format、isSave 初始化日志。
5. `EnableTrace` 时初始化 Jaeger provider，采样率来自配置。
6. `EnableStat` 时启动进程 CPU/内存统计及报警。
7. `database.InitDB` 根据 driver 建立 SQL 连接池。
8. `database.InitCache` 选择 memory、redis 或不使用缓存。

顺序不能随意换：数据库日志需要 logger；数据库与 Redis tracing 需要 tracer provider；所有后续构造函数都假定 `config.Get()` 已经可用。

## 4. CreateServices 是手工依赖注入的组合根

HTTP 地址由 `":" + strconv.Itoa(cfg.HTTP.Port)` 产生，传给 `server.NewHTTPServer`；选项注入生产模式、TLS、可选注册中心。gRPC 同理使用 `cfg.Grpc.Port`。组合型入口把两个 server 都放入 `[]app.IServer`。

这里没有 Wire/Fx 容器，依赖注入完全依赖构造函数：

```text
CreateServices
  -> NewHTTPServer -> routers.NewRouter -> init 注册的路由 -> NewHandler
  -> NewGRPCServer -> RegisterUserExampleServer(NewUserExampleServer())
  -> Handler/Service -> NewDao(GetDB(), NewCache(GetCacheType()))
```

优点是调用关系透明；代价是构造逻辑会散落在 handler/service 构造器中。重实现时可先照此做，等测试稳定后再抽成显式 `Dependencies`。

## 5. Start：为什么会阻塞

`app.Run` 通常为每个服务启动 `Start` 并监听退出信号。HTTP 的 `httpsrv.Server.Run()` 和 gRPC 的 `grpc.Server.Serve(listener)` 都是阻塞调用，这不是死循环错误，而是服务器正常驻留方式。若配置注册中心，`Start` 先用 5 秒 context 注册实例。

gRPC 若启用 metrics 或 profile，还会额外启动一个 `Grpc.HTTPPort` 上的 HTTP server；真正 gRPC listener 会被 metrics listener 包装，以统计连接。

## 6. Close：退出时发生什么

`initial.Close` 构造一组回调，依次包含：

1. 每个 server 的 `Stop`；
2. `database.CloseDB`；
3. cacheType 为 redis 时 `database.CloseRedis`；
4. trace 开启时，用 2 秒 context flush/close；
5. `logger.Sync` 冲刷日志。

HTTP `Stop` 先在最多 2 秒内注销服务实例，再用 3 秒 `Shutdown` 等待在途请求。gRPC 使用 `GracefulStop`，然后关闭 metrics/profile HTTP server。注意源码的 registry 注销用 goroutine + context，目标是无论注册中心是否响应都不永久卡住退出。

## 7. 新手容易犯的错误

- 在 `config.Init` 前调用 `config.Get`：会直接 panic。
- 在 logger 之前初始化数据库：连接日志使用未初始化 logger。
- 把 `Start` 当普通函数顺序调用多个服务：第一个阻塞，第二个永远启动不了；必须由 app 并发调度。
- 只关闭 listener，不调用 graceful shutdown：在途请求被切断，trace/log 可能丢失。
- `sync.Once` 初始化失败后希望自动重试：Once 已消耗，生产代码应明确失败并退出。
- 把示例默认 gRPC appKey 投产：该值只是模板占位，真实系统应从密钥系统或数据库校验。

## 8. 按源码重实现

1. 定义 `IServer` 与 `App.Run`，先用一个假 server 测试 signal 和关闭顺序。
2. 实现配置单例与 `-c/-version` 覆盖。
3. 依次加入 logger、trace、stat、DB、cache 初始化。
4. 实现 HTTP server 的 Start/Stop，再实现 gRPC。
5. 让 `CreateServices` 只负责组装，不放业务逻辑。
6. 给每个资源实现幂等 Close，并用超时保护外部网络清理。
7. 测试启动失败、一个服务提前退出、SIGTERM、有在途请求四种路径。

## 9. 阅读断点

从 `main.main` 开始，依次在 `InitApp`、`config.Init`、`database.InitDB`、`CreateServices`、`NewHTTPServer/NewGRPCServer`、`app.Run`、各 `Start`、各 `Stop` 打断点。这样看到的是运行时真实顺序，而不是目录顺序。
