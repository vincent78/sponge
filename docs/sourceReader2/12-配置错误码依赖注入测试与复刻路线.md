# 12 配置、错误码、依赖注入、测试与完整复刻路线

## 1. 配置结构

`internal/config/serverNameExample.go` 由配置生成器产生。`Config` 聚合 App、HTTP、Grpc、GrpcClient、Database、Redis、Logger、Jaeger、Consul/Etcd/Nacos。`Init(file)` 创建新对象并用 `conf.Parse` 填充；`Get` 在未初始化时 panic；`Show` 序列化用于日志/调试；`Set` 主要方便测试替换。

`serverNameExample_cc.go` 定义配置中心引导配置 `Center/Nacos`：本地小配置告诉程序去哪里取远端大配置。二者不要混淆。

配置字段影响路径：

| 字段 | 运行时效果 |
|---|---|
| `app.env` | Gin release/debug，是否暴露 config/swagger |
| `app.cacheType` | nil/memory/redis cache |
| `enableTrace/Metrics/Limit/CircuitBreaker` | 中间件、拦截器、client option |
| `http.port/tls/timeout` | HTTP listener 和全局超时 |
| `grpc.port/httpPort/serverSecure/enableToken` | gRPC、观测端口、TLS/token |
| `database.driver` | 选择数据库实现 |
| `grpcClient[]` | 下游连接、TLS、token、timeout、发现 |

生产中打印配置要隐藏 DSN、password、appKey、证书私钥路径等字段；`/config` 只能非生产开放仍需确认环境值可靠。

## 2. 错误码组织

`internal/ecode/systemCode_http.go` 与 `_rpc.go` 是系统级错误；`userExample_http.go` 与 `_rpc.go` 是实体业务错误。分开 HTTP/RPC 是因为传输状态映射不同，但业务 code 应保持唯一、稳定、可文档化。

建议错误流程：底层返回可判定 error（`errors.Is`）→ 业务层记录内部细节 → 映射为稳定 ecode → transport 输出 HTTP JSON 或 gRPC status。客户端不应解析错误 message，应该判断 code。

新增错误时检查：编号是否冲突、HTTP/gRPC 状态是否合适、message 是否泄密、是否应重试、日志级别、监控是否把它计为失败。

## 3. 当前依赖注入方式

项目使用构造函数注入和接口隔离：

```text
config/database/cache 是进程级 provider
NewCache(CacheType)
NewDao(DB, Cache)
NewHandler/NewService 内部调用 provider
NewRouter/NewGRPCServer 注册业务对象
CreateServices 提供 server 给 App
```

`var _ Interface = (*impl)(nil)` 是零成本编译期检查。DAO/Cache 定义接口便于替换；但 Handler 的无参构造器把 DB 构造藏在内部，不利于单测。复刻时建议保留便利构造器，同时提供显式构造器：

```go
func NewUserHandler(d dao.UserExampleDao) UserHandler
func NewDefaultUserHandler() UserHandler {
    return NewUserHandler(dao.NewUserExampleDao(database.GetDB(), ...))
}
```

这样组合根负责真实依赖，测试直接传 fake。

## 4. 源码中的测试分层

- `internal/config/*_test.go`：解析、Get/Set、配置展示；
- `internal/database/init_test.go`：初始化/关闭与错误路径，部分使用超时保护；
- `internal/cache/*_test.go`：memory/redis 行为；
- `internal/dao/*_test.go`：CRUD、分页、事务；
- `internal/handler/*_test.go`：Gin handler/logic；
- `internal/service/*_test.go`：gRPC service 逻辑与 client；
- `internal/routers/*_test.go`、`internal/server/*_test.go`：路由和服务器选项。

模板测试中可能依赖本地 MySQL/Redis 或用 recover 忽略连接失败。重新实现时应把“纯单测”和“外部依赖集成测试”分开，通过 build tag、环境变量或容器显式选择，不能让 CI 悄悄跳过核心断言。

## 5. 推荐测试金字塔

1. DTO/validate/query 转换纯单测，数量最多；
2. Handler/Service + fake DAO，验证业务分支；
3. SQLite + memory cache 的 DAO 集成测试；
4. `httptest` HTTP 路由测试与 `bufconn` gRPC 测试；
5. 少量 MySQL/Postgres/Redis 容器契约测试；
6. 进程级启动、SIGTERM、Gateway、TLS 的端到端测试。

所有失败路径至少断言：外部 status/code、是否调用 DAO、是否泄漏内部错误、request ID 是否存在。并发相关测试运行 `go test -race`。

## 6. 从零复刻的阶段路线

### 阶段 A：最小垂直闭环

定义 User model 和 DAO 接口；内存实现 Create/Get；写一个 HTTP POST/GET；统一 success/error JSON；用 httptest 通过。这一步不接数据库、不上缓存。

### 阶段 B：真实 SQL

加入配置解析、SQLite、GORM model、DAO CRUD、分页与字段白名单。让 HTTP 使用真实 DAO，补 not found 和 rollback 测试。

### 阶段 C：运行时工程化

加入 logger、request ID、recovery、timeout、graceful shutdown。定义 `IServer/App`，让 SIGTERM 测试确认在途请求完成并关闭 DB。

### 阶段 D：Proto 与 gRPC

把 API 契约写入 proto，生成代码，实现同一 DAO 上的 service；加 validate、ecode/status 映射和 bufconn 测试。然后增加 gateway 或 Proto-Gin，二选一先跑通。

### 阶段 E：缓存与韧性

先 memory cache-aside，再 singleflight/placeholder，再 Redis。逐项增加 metrics、trace、rate limit、circuit breaker；观察开关关闭时的基线行为。

### 阶段 F：安全与发布

启用鉴权，替换示例 appKey；加入 TLS/mTLS；隐藏敏感配置；做输入上限、SQL 白名单、依赖超时、健康检查；最后加入服务注册发现。

## 7. 每阶段客观验收

- A：Create 后 Get 数据一致，非法 JSON 得稳定 4xx code。
- B：CRUD/分页/事务测试通过，非法列名不能进入 SQL。
- C：panic 不退出进程，request ID 串起日志，SIGTERM 在超时内结束。
- D：HTTP 与 gRPC 对相同输入输出一致业务 code，非法 proto 被 Validate 拦截。
- E：第二次 Get 命中缓存，并发 miss 不击穿，不存在 ID 有负缓存。
- F：无 token/TLS 失败，敏感字段不出现在日志和 `/config`，实例能注册与注销。

## 8. 新手阅读顺序与动手法

按 `cmd/.../main.go` → `initial` → `internal/server` → `routers` → `handler/service` → `types/proto` → `dao` → `cache` → `database` → `model` → `ecode` 的顺序。每读一个函数都写四句话：谁调用它、输入是什么、输出/副作用是什么、失败如何传播。然后画出一次 Create 与 Get 的时序，并用断点验证。

不要一开始复制全部代码。先复刻最短可运行链，每多加一个组件就写测试；这样文档中的每个主题都是一次可验证的增量，而不是一次无法调试的大搬运。
